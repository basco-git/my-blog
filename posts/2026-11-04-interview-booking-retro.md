## 1. 문제 정의: 면접 한 건에 메일이 몇 번 오가나요? 📨

채용 담당자라면 다들 아실 거예요. 면접 한 건을 잡는 과정은 이래요.

1. 면접관 2~3명에게 가능한 시간을 묻는다.
2. 답이 다 모이면 겹치는 시간을 찾아 후보자에게 전달한다.
3. 누군가 한 명이 시간을 바꾸면… **처음부터 다시.** 🔁
4. 가끔은 같은 시간에 두 후보자가 겹쳐 잡히기도 한다. 😱

그래서 "일정 조율 도구"가 아니라, 딱 한 문장을 서비스의 중심에 뒀어요.

> 🎯 **면접관들이 각자 링크로 가능한 시간을 표시하면, 면접관이 충분히 모인 시간만 후보자에게 열리고, 후보자가 링크로 직접 골라 예약한다.**

| 사용자 | 들어오는 방법 | 하는 일 |
|---|---|---|
| 🧑‍💼 HR 담당자 | 가입 후 관리자 승인 | 포지션과 시간 후보를 만들고 링크를 전달 |
| 👥 면접관 (2~3명) | 개인 링크 (로그인 없음) | 가능한 시간 체크 |
| 🙋 후보자 | 개인 링크 (로그인 없음) | 열린 시간 중 하나를 예약하거나 변경 |

면접관과 후보자에게 가입까지 요구하면 응답이 늦어지고 개인정보도 늘어나요. 그래서 **링크만으로 들어오고, 이름만 받기**로 정했어요.

## 2. 이틀 안에 끝내려면: 범위 자르기 ✂️

| 구분 | 내용 |
|---|---|
| ✅ **꼭(Must) 3개** | ① 시간 후보 만들기 + 면접관 체크 ② 인원이 모인 시간만 열림 + 후보자 예약 ③ 담당자가 한 화면에서 현황 보기 |
| ➕ **먼저 붙인 것** | 후보자의 시간 **변경** (현업에서 변경 요청이 가장 잦아서) |
| ❌ **지금은 안 함** | 캘린더 연동, 메일·문자 자동 발송, 평가표·합격 관리, 화상면접 링크, 회의실 예약, 다국어·결제 |

가장 아까웠던 건 **캘린더 연동**이에요. 면접관 캘린더를 읽어 오면 체크 자체가 필요 없으니까요.
하지만 외부 로그인(OAuth)·권한·동기화까지 하루 안에 검증할 수는 없었어요. 대신 **링크로 체크만 받는 방식**으로 문제의 대부분을 먼저 풀었어요.

PRD 초안을 받은 뒤에는 **현업 기준으로 다시 손봤어요.** 면접 시간은 15분 단위로, 면접관은 2~3명이 함께 들어가는 경우를 기본으로, 담당자 혼자가 아니라 HR 팀이 함께 관리하도록요. 이런 조건은 AI가 먼저 떠올려 주지 않아요. 현장을 아는 사람의 몫이었어요.

Todo 과제에서 써 본 **Supabase + 프레임워크 없는 HTML·CSS·JS**를 골랐어요. 화면이 3개뿐이라 빌드 도구는 오히려 짐이었고, 서버가 없으니 GitHub Pages에 바로 올릴 수 있었어요.

### 핵심 설계: 문지기는 화면이 아니라 DB 🚪

처음엔 규칙을 화면에서 막으려 했어요. 예약된 시간은 버튼을 숨기는 식으로요.
그런데 버튼을 숨겨도 **링크로 직접 요청을 보내면 그만**이에요. 그래서 모든 규칙을 **데이터 저장 쪽(DB)에서** 막기로 했어요.

| # | 규칙 | 막는 곳 |
|---|---|---|
| R1 | 한 시간에 후보자 한 명 | 예약 표의 고유 제약 + 예약 함수가 시간 행을 잠금 |
| R2 | 링크 하나에 예약 하나 (다시 고르면 변경) | 후보자별 고유 제약 |
| R3 | 면접관이 모자란 시간은 예약 불가 | 예약 함수가 가능 인원 확인 |
| R4 | 예약된 시간은 면접관이 체크 해제 불가 | 체크 함수가 예약 여부 확인 |
| R6 | 승인된 담당자만 일정 관리 | 모든 표에 RLS |
| R7 | 링크로는 자기 것만 | 링크 사용자는 표에 직접 접근 불가, 토큰 함수 4개로만 |
| R9 | 시간 겹침 금지 · 15분 단위 | 배제 제약(EXCLUDE) + CHECK |

> 💡 **HR식으로 이해하기**: 회사 출입을 안내 데스크 직원의 기억력에 맡기지 않고 **출입 게이트**에 맡기는 것과 같아요. 화면은 안내 데스크, DB는 게이트예요. 안내를 건너뛰어도 게이트는 못 지나가요.

### 검증: "된다"를 숫자로 확인하기 ✅

| 단계 | 결과 |
|---|---|
| 내 컴퓨터 PostgreSQL에서 규칙 시험 | 19/19 통과 |
| **같은 시간에 예약 요청 10건 동시 발송** | **1건만 성공**, DB 예약도 1건 |
| 실제 Supabase에 규칙을 어기는 요청 보내기 | 21/21 → 공유·승인 기능 뒤 25/25 → 면접 완료 기능 뒤 **28/28** |
| 배포 주소에서 담당자·면접관·후보자 화면 직접 클릭 | PRD 성공 조건 3개 통과 |

동시 예약 10건 중 딱 1건만 성공한 걸 확인한 순간이 이번 프로젝트에서 제일 짜릿했어요. 현업에서 겪었던 "같은 시간 두 후보자" 사고가 구조적으로 막힌 거니까요. 🎉

## 5. 문제 해결 경험 🔧

### ① 가만히 있어도 화면이 사라졌다

후속 기능을 붙이던 중, 이상한 오류가 생겼어요. 포지션 상세 화면을 열어 두면 **아무것도 안 해도** 몇 초 뒤 포지션 목록으로 저절로 넘어가 버렸어요. 면접관을 추가하려다 화면이 사라지니 서비스를 쓸 수 없는 수준이었죠.

당시 쓰던 AI 모델에 수정을 맡겼는데, 모델은 계속 **"뒤로가기 동작"** 을 의심했어요.

| 시각 | 시도 | 결과 |
|---|---|---|
| 17:14 | 트랙패드 가로 스와이프로 이탈하지 않게 | 그대로 |
| 17:19 | 스와이프 오작동 추가 방지 | 그대로 |
| 17:21 | 세로 스크롤도 뒤로가기로 보지 않게 | 그대로 |
| 17:25 | 상세 화면에서 뒤로가기·스와이프 전부 무시 | 그대로 |
| 17:31 | 상세 화면을 강제로 고정 | 그대로 |
| 17:37 | **자동 갱신이 상세 화면을 덮던 오류 수정** | **해결** ✅ |

20여 분 동안 증상만 막는 커밋이 6개 쌓였어요. 그런데 생각해 보면 **"가만히 있어도 넘어간다"** 는 것 자체가, 스와이프나 뒤로가기 같은 **사용자 입력과는 관계없다**는 단서였어요.

그래서 모델에게 계속 맡기지 않고, 제가 직접 개발자 도구로 **"몇 초 뒤에 넘어가는지", "무엇을 안 해도 넘어가는지"** 를 반복해서 관찰하고 검색으로 원인을 좁혔어요.
범인은 다른 담당자의 변경을 반영하려고 **5초마다 도는 자동 갱신**이었어요.

```js
// 고치기 전: true를 '지금 보던 포지션 ID'로 읽음 → 그런 ID가 없으니 목록으로
loadPositions(true);

// 고친 뒤: 지금 보던 포지션 ID를 넘기고, 문자열일 때만 ID로 씀
loadPositions(state.position && state.position.id);
const requested = typeof keepId === "string" ? keepId : options.currentId || previous;
```

고친 건 **단 3줄**이었어요. 😅

> 💡 **배운 것**
> - **증상을 정확히 관찰하는 게 먼저**예요. "언제, 무엇을 하지 않아도" 일어나는지가 원인을 가리켜요.
> - **같은 방향으로 두 번 실패하면 멈춰야** 해요. 작업 규칙에 "두 번 고쳐도 안 되면 멈추고 보고"라고 적어 뒀는데도 도구가 지키지 않았어요.
> - **모델마다 디버깅 능력 차이가 커요.** 그 모델은 화면 생성은 빨랐지만 원인 추적은 약했어요. 앞으로는 **새 기능은 빠른 모델, 원인 추적과 검증은 믿을 만한 모델**로 나눠 쓰려고 해요.

### ② 시험이 엉뚱한 이유로 "통과"했다

로컬 시험에서 "거부돼야 하는 요청이 거부됨 → 통과"로 찍혔는데, 알고 보니 **한글 깨짐과 줄 끝 문자 때문에 생긴 다른 오류**가 "거부됨"으로 잡힌 거였어요.
그래서 **기대한 거부 문구가 정확히 나올 때만** 통과로 치도록 시험을 고쳤어요.

> 💡 실패해야 하는 시험은, **왜** 실패했는지까지 확인해야 진짜 통과예요.

### ③ 기능은 바꿨는데 시험은 그대로였다

"담당자는 자기 포지션만 본다"던 규칙을 "승인된 담당자끼리 함께 본다"로 바꿨는데, PRD에는 옛 규칙의 "통과" 기록이 그대로 남아 있었어요.
승인 대기 계정을 하나 더 만들어 R6를 다시 시험했고(25/25), **"기능을 바꾸면 시험과 기록도 함께 바꾼다"** 를 작업 규칙에 추가했어요.

### ④ 마감 전날의 스코프 크립

마감 전날 회원 승인, 담당자 공유, 브랜드 로고, 뒤로가기 처리가 연달아 붙었어요. 하나하나는 그럴듯했지만, 앞의 오류도 이 시기에 생겼어요.
점검 뒤에는 **기능 추가를 멈추고 검증과 제출만** 했어요. "안 함" 목록은 첫날보다 **마지막 날에 더 중요**하더라고요.

- 📝 **진행 기록과 인수인계서를 커밋마다**: 새 도구에서도 "`handoff.md` 읽고 이어서" 한 줄이면 바로 이어 갔어요.
- 💾 **작동하면 저장**: 커밋마다 확인한 결과를 메시지로 남겨, 도구를 세 번 바꿔도 어디까지 됐는지 바로 알 수 있었어요.

> 💡 **느낀 점**: 인사팀에서 담당자가 바뀔 때 가장 중요한 게 인수인계서잖아요. AI 도구도 똑같았어요. **기억은 도구가 아니라 문서에 남겨야** 누가 와도 이어서 일할 수 있어요.

지금 가장 겁나는 건 **실제 사용자를 받는 것**이에요. 지금은 링크를 가진 사람이 그 링크의 일을 할 수 있는 구조라, 링크가 새면 담당자가 사람을 지우고 다시 만들어야 해요. 실제 지원자 정보를 다루려면 링크 만료, 접근 기록, 개인정보 보관 기간까지 갖춰야 해요. HR을 오래 해 온 만큼, 이 부분의 무게를 누구보다 잘 알고 있어요.

## 8. 더 알아보고 싶은 것 & 다음 목표 🎯

1. 📆 **캘린더 연동**: OAuth를 공부해서, 면접관이 체크하지 않아도 가능한 시간을 읽어 오기
2. 📧 **알림 메일**: 예약·변경이 생기면 면접관과 후보자에게 자동으로 알리기
3. 🧪 **화면 자동 시험**: 자동 갱신이 보던 화면을 덮지 않는지 확인하는 시험 추가 (이번 오류의 재발 방지)
4. 🔐 **개인정보 설계**: 링크 만료, 접근 기록, 보관 기간

> 🎯 **목표**: at~once를 **실제 채용 담당자가 써도 안심할 수 있는** 서비스로 키우기. 그리고 그 과정에서 얻은 "문지기는 DB", "기억은 문서에"를 다음 HR 앱에도 그대로 가져가기!
