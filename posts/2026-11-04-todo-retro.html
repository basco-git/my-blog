1. 문제 정의: 할 일 앱, 그런데 "진짜 서비스"처럼 🎯

Todo 앱은 세상에 정말 많죠. 그래서 이번 과제의 핵심은 기능 개수가 아니라 서비스 한 바퀴였어요.
시작하면서 스스로에게 던진 질문은 세 가지였습니다.

질문확인할 것
🗄️ 서버를 껐다 켜도 할 일이 남을까?저장: 새로고침·재시작 뒤에도 데이터 유지
🔐 다른 사람이 로그인하면 내 할 일이 안 보일까?권한: 로그인한 본인의 데이터만
🤖 AI에게 내 데이터를 맡겨도 안전할까?AI 연동: AI도 화면과 똑같은 검사를 거치게

기능은 할 일 추가·완료·삭제에 마감일 색 표시, 태그, 오늘의 할 일, 검색, 그리고 기간 재설정(미룬 이유와 횟수 기록) 까지 넣었어요. 미룬 횟수가 쌓이는 걸 보면 저절로 반성하게 돼요. 😇
대신 알림, 반복 일정, 공유는 처음부터 범위 밖으로 뺐어요.

2. 내가 맡은 역할과 직접 구현한 기능 🛠️

개인 과제라 기획부터 배포까지 전부 제 몫이었어요. 코드는 Claude Code와 함께 썼지만, 무엇을 만들지 정하고 된 것을 확인하는 건 제가 했어요.

역할한 일
📋 기획PRD 작성: 기능, 저장 요구사항, 규칙(무료 도구만, 비밀값은 .env), 완료 기준
🗄️ DB 설계코드보다 구조도(ERD)를 먼저. 할 일 · 태그 · 할 일↔태그 연결 · 마감일 변경 기록, 표 4개
⚙️ 백엔드Flask API(할 일·태그·마감일 재설정·로그인), 저장소 모듈 2개(SQLite용 · Supabase용)
🔐 보안Supabase Auth 로그인, 모든 표에 RLS(user_id = auth.uid()), 관리자 키(service_role) 쓰지 않기
🌐 배포render.yaml 한 파일로 Render 배포, Supabase 인증 설정 정리
🤖 AI 연동터미널 명령 todo, 작업 규칙 AGENTS.md, 스킬 todo-summary, MCP 서버 todo-files

3. 기술적 수행 과정 🧭

한 번에 다 만들지 않고, 길 A → 길 B → 배포 → 길 C 순서로 단계마다 확인하며 키워 갔어요.

단계한 일확인한 것
💻 길 A로컬 SQLite 파일 하나로 완성서버 끄고 켜도 할 일 3개 그대로
☁️ 길 BSupabase + 이메일 로그인 + RLS계정 B로 들어가면 A의 할 일 0개
🌐 배포Render 무료 플랜에 길 B만 배포공개 주소에서 열림, 비로그인 요청 차단
🤖 길 CAI 도구가 할 일을 다루는 통로 만들기AI도 로그인·RLS를 거쳐야만 데이터 접근

💡 설계 포인트 ① 저장소만 갈아 끼우기

길 A에서 길 B로 넘어갈 때 화면과 API 코드는 한 줄도 바꾸지 않게 만들었어요. 바뀌는 건 백엔드의 저장소 모듈뿐이에요.

브라우저 → /api/* → app.py ─┬→ store_sqlite.py   → todo.db (내 컴퓨터)
                            └→ store_supabase.py → Supabase (RLS가 지킴)
# .env 한 줄로 전환
DB_BACKEND=sqlite     # 길 A
DB_BACKEND=supabase   # 길 B

HR로 치면 업무 절차는 그대로 두고 보관 창고만 옮긴 셈이에요. 창고를 옮겼다고 결재 라인을 다시 짤 필요는 없으니까요.

💡 설계 포인트 ② AI용 뒷문을 따로 만들지 않기

길 C에서는 Claude Code 같은 AI 도구도 할 일을 다룰 수 있게 했어요. 가장 쉬운 방법은 AI에게 DB 파일을 그냥 열어 주는 거지만, 그러면 화면에서 하던 입력 검사·로그인·RLS를 전부 건너뛰게 돼요.

그래서 터미널 명령 todo가 웹 화면과 똑같은 API를 그대로 부르게 만들었어요. AI 전용 통로가 없으니 지켜야 할 규칙도 한 벌이면 돼요.

장치하는 일
⌨️ todo 명령add · list · done · summary. 앱 API를 그대로 불러 같은 검사 적용
📜 AGENTS.md데이터는 todo 명령으로만, 바꾸거나 지우기 전엔 반드시 확인, 비밀값 출력 금지
✨ 스킬 todo-summary오늘 완료한 일을 커밋 메시지 형식으로 정리
📂 MCP todo-filesdocs·frontend·backend 폴더만 열기. .env·todo.db가 있는 폴더는 Access denied

🙋 실제로 "이 파일 지워 줘"라고 했더니, AI가 바로 지우지 않고 경로·크기·내용·git 추적 여부를 먼저 보여 주고 확인을 받았어요. 덕분에 이름이 비슷한 다른 파일을 지울 뻔한 걸 미리 알 수 있었어요.

4. 문제 해결 경험 🔧

① 날짜 검사에 구멍이 있었다

PRD에 "날짜는 날짜 형식으로 저장하고, 틀린 값은 거부"라고 적었는데, SQLite에는 날짜 타입이 따로 없어요. 그래서 형식 검사(CHECK)로 막기로 했죠.
그런데 처음 만든 검사는 잘못된 날짜도 통과시키고 있었어요. 코드를 읽어서는 몰랐고, 실제로 이상한 날짜를 넣어 보는 테스트에서 드러났어요.

-- 날짜로 바꿔 본 값이 원래 값과 똑같을 때만 통과
due_date DATE CHECK (due_date IS NULL OR date(due_date) IS due_date)

💡 배운 것: "검사를 만들었다"와 "검사가 막는다"는 다른 이야기예요. 막아야 할 값을 직접 넣어 봐야 알 수 있어요.

② 배포했더니 인증 메일이 localhost로 갔다

Render 배포까지 마치고 새 계정으로 가입해 봤는데, 인증 메일의 링크를 누르니 localhost로 가 버렸어요. 😵
원인은 코드가 아니라 Supabase 대시보드의 Site URL 설정이었어요. 배포 주소로 바꾸고 나서야 가입이 제대로 이어졌어요.

💡 배운 것: 배포는 코드만 올리는 게 아니에요. 코드 밖에 있는 설정(인증 주소, 비밀값, 무료 서버 잠들기)까지 함께 옮겨야 해요.

③ .bat 파일이 한글 주석을 명령으로 읽었다

더블클릭으로 앱을 켜는 start.bat, 터미널 명령 todo.bat을 만들었는데, cmd가 한글 주석 줄을 명령으로 읽고 오류를 냈어요.
원인은 줄바꿈 방식이었어요. 파일이 LF로 저장돼 있었는데, cmd는 CRLF를 기대해요. CRLF로 바꿔 해결하고, 같은 실수를 반복하지 않게 AGENTS.md에 규칙으로 남겼어요.

④ 캡처에는 있는데 저장소에는 없던 스킬 파일

제출 직전 점검에서 깜짝 놀랐어요. 스킬이 실행되는 캡처는 문서에 있는데, 정작 스킬 파일이 저장소에 없었어요.
저장소의 .gitignore가 .claude/ 폴더를 통째로 빼고 있었던 거예요. 점검을 안 했다면 "캡처만 있고 파일은 없는" 상태로 제출할 뻔했어요.

💡 배운 것: 문서에 건 링크가 실제로 git에 올라가 있는지 확인하는 단계가 필요해요. 그래서 이후에는 제출 전 점검을 스킬로 만들어 매번 돌리고 있어요.

⑤ AI가 대신 못 하는 일은 사람 몫

막힌 곳해결
Supabase 대시보드 화면이 안내와 달라 설정 위치를 못 찾음안내와 다른 화면에서 메뉴를 하나씩 직접 찾아감
SQL Editor에 파일 내용 대신 파일 경로를 붙여 넣음 😂오류 문구를 다시 읽고 내가 뭘 넣었는지부터 확인
Render 저장소 연결 화면에서 막힘공개 저장소 주소를 직접 붙여 넣는 방법으로 해결

계정 만들기, 키 확인, 회원가입은 AI가 대신할 수 없어요. 이 부분에서 가장 오래 헤맸고, 그만큼 서비스가 어떤 부품으로 이어져 있는지 몸으로 익혔어요.

5. 협업: 짝꿍과 서로 코드 리뷰 👥

과제 마지막에는 짝을 정해 서로의 GitHub 저장소를 공유하고, Claude로 상대 코드를 리뷰한 뒤 그 내용을 전달했어요.

짝꿍은 Todo 앱에 구글 캘린더 연동까지 도전하고 있었어요. 같은 과제를 받았는데 저는 "할 일을 잘 저장하기"에 집중했고, 짝꿍은 "할 일을 내 일정과 잇기"를 상상했더라고요.
외부 서비스를 연결하는 코드는 인증과 권한이 얽혀 까다로워서, 리뷰하면서 저도 덩달아 공부가 됐어요.

💡 느낀 점: 남의 코드를 리뷰하려면 상대가 무엇을 만들려 했는지부터 이해해야 해요. 면접에서 지원자의 이력서를 읽기 전에 직무 기술서를 먼저 보는 것과 비슷했어요.
